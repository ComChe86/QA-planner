# QA Test Planner

## Мета

Допомогти QA-інженеру швидко створювати якісну тестову документацію: тест-плани, ручні тест-кейси, регресійні набори та баг-репорти — без втрати структури та повноти.

Skill не замінює аналіз вимог. Якщо вимога сира або неоднозначна — спочатку варто провести requirements review skill'ом `requirements-review-skill`, і лише потім переходити до тест-планування. Якщо в цьому чаті вже є вердикт `Не готова` або `Потребує уточнень` — не роздувай тест-кейси поверх дірок; познач блокери і запропонуй уточнити вимогу. Якщо є блок **Готові факти** з рев'ю — бери його як інвентар заявленої поведінки і не вигадуй сценарії поза ним.

---

## Активація

Skill використовує явне тригерування — його треба викликати за назвою:

- `/qa-test-planner`
- `qa-test-planner`
- «використай скіл qa-test-planner»

## Як це працює: три фази

### 1. Аналіз

- розбирає опис фічі, вимогу або баг;
- якщо в чаті є звіт `requirements-review-skill` — бере блок **Готові факти** як інвентар заявленої поведінки;
- якщо в фактах є TO-BE / нова норма — будуй кейси з неї, не з AS-IS і не з історії продукту;
- якщо в фактах є точний текст повідомлення, строк з точкою відліку або заявлена відправка — бери їх як є; не вигадуй timezone, HTML-шаблон чи інший канал;
- якщо в фактах є список, фільтр, поле пошуку, розмір сторінки або текст empty — бери їх як є; не вигадуй пагінацію, debounce чи нечіткий пошук;
- визначає, який тип тестування потрібен (функціональне, UI, інтеграційне, регресійне);
- визначає обсяг, пріоритети та ключові edge cases, які прямо випливають з опису або з готових фактів.

### 2. Генерація

- створює документ за перевіреним шаблоном (див. `references/`);
- застосовує QA-практики за замовчуванням (пріоритети, severity, precondition/postcondition);
- додає edge cases, які прямо випливають із контексту — без вигадування бізнес-логіки, якої не було надано.

### 3. Валідація

Перед тим як віддати результат, перевір:

- чи є трасування між вимогою і тест-кейсами (кожен кейс покриває конкретний пункт вимоги);
- чи кожен крок має очікуваний результат;
- чи документ логічно завершений (немає обірваних кроків чи пропущених розділів шаблону).

## Типи результатів (deliverables)

### 1. Тест-план

Повний тест-план містить:

- executive summary — мета та ризики;
- обсяг (що входить / що не входить);
- стратегія та підхід до тестування;
- вимоги до середовища;
- критерії входу та виходу;
- оцінку ризиків із заходами пом'якшення;
- таймлайн і артефакти.

### 2. Ручні тест-кейси

Кожен тест-кейс містить:

- покрокові дії;
- очікуваний результат для кожного кроку;
- передумови (preconditions) та тестові дані;
- пріоритет (P0–P3);
- postconditions / очищення після тесту;
- edge cases і варіації, якщо вони прямо випливають із опису фічі.

Формат нумерації: `TC-МОДУЛЬ-###` (наприклад, `TC-CHECKOUT-001`).

### 3. Регресійні набори

Багаторівневі набори:

| Рівень | Час виконання | Що покриває |
|---|---|---|
| Smoke | 15–30 хв | Тільки критичні шляхи |
| Sanity | 10–15 хв | Швидка перевірка після hotfix |
| Targeted regression | 30–60 хв | Області, які зачепила зміна |
| Full regression | 2–4 год | Повне покриття |

### 4. Валідація дизайну (Figma)

Якщо підключено Figma MCP:

- дістає специфікації дизайну (кольори, відступи, типографіку);
- порівнює реалізацію з дизайн-системою;
- формує чек-лист валідації UI;
- фіксує візуальні розбіжності як баги.

Якщо Figma MCP не підключено — цей розділ пропускається, skill не вигадує специфікації.

### 5. Баг-репорти

Структурований баг-репорт містить:

- чіткі кроки відтворення;
- деталі середовища (ОС, браузер, пристрій, білд);
- очікувану та фактичну поведінку;
- візуальні докази (скріншоти, відео, консольні логи — якщо надані);
- severity та priority;
- оцінку впливу та можливі workaround'и.

Формат заголовка: `[Модуль] Короткий опис проблеми` (наприклад: `[Форма контактів] Відправка дозволена з порожнім email`).

## Основні правила

1. **Аналізуй тільки наданий контекст.** Не вигадуй бізнес-логіку, архітектуру чи UI-деталі, яких немає в описі.
2. **Один тест-кейс = одна перевірювана поведінка.** Не змішуй кілька незалежних сценаріїв в один кейс.
3. **Кожен крок повинен мати очікуваний результат.** Крок без очікуваного результату — неповний тест-кейс.
4. **Не вигадовуй тестові дані, яких не можна вивести з контексту** — якщо конкретні значення не задані, познач це як «уточнити з BA/QA lead» замість вигаданих чисел.
5. **Пріоритет і severity признач обґрунтовано**, а не за замовчуванням «High» для всього.
6. **Дотримуйся обраного шаблону з `references/`** — не змінюй структуру документа довільно.

## Пріоритети та Severity

### Пріоритет тест-кейсу (P0–P3)

- **P0** — критичний шлях, блокує основний функціонал.
- **P1** — важлива функціональність, високий вплив на користувача.
- **P2** — другорядна функціональність або рідкісний сценарій.
- **P3** — косметичні або дуже рідкісні кейси.

### Severity бага

- **Critical** — система недоступна або дані втрачаються/пошкоджуються.
- **High** — основна функціональність не працює, немає обхідного шляху.
- **Medium** — функціональність порушена частково, є workaround.
- **Low** — косметична або незначна проблема.

## Чек-листи якості

### Тест-план

- [ ] Обсяг чітко визначений (in/out of scope)
- [ ] Критерії входу та виходу вказані
- [ ] Ризики визначені з заходами пом'якшення
- [ ] Таймлайн реалістичний

### Тест-кейс

- [ ] Кожен крок має очікуваний результат
- [ ] Передумови задокументовані
- [ ] Тестові дані вказані або позначені як «уточнити»
- [ ] Пріоритет призначений (P0–P3)
- [ ] Edge cases включені, якщо випливають з опису

### Баг-репорт

- [ ] Кроки відтворення відтворювані
- [ ] Середовище задокументоване повністю
- [ ] Severity та priority встановлені обґрунтовано
- [ ] Є місце для доказів (скріншоти/відео/логи)

## Чого уникати (антипатерни)

| Уникай | Чому це погано | Що робити натомість |
|---|---|---|
| Розмиті кроки тесту | Неможливо відтворити стабільно | Конкретні дії з конкретним очікуваним результатом |
| Відсутні передумови | Тести падають неочікувано | Задокументувати всі умови налаштування |
| Немає тестових даних | Тестувальник блокується | Дати приклад даних або позначити «уточнити» |
| Загальні заголовки багів | Складно відстежувати й пріоритезувати | Конкретика: «[Модуль] проблема при [дії]» |
| Пропуск edge cases, які прямо випливають з опису | Пропускаються реальні баги | Включати межові значення, null, порожні стани |
| Вигадані edge cases, яких немає в описі | Роздуває документ і плутає пріоритети | Виносити як окреме питання, а не в тест-кейс |

## Перед фінальною відповіддю перевір себе

1. Чи кожен тест-кейс/крок дійсно випливає з наданого опису?
2. Чи не вигадав я тестові дані, специфікації дизайну чи бізнес-правила?
3. Чи призначені пріоритет і severity обґрунтовано, а не за замовчуванням?
4. Чи документ відповідає обраному шаблону без довільних змін структури?
5. Чи є трасування між вимогою (або готовими фактами рев'ю) і тест-кейсами?
6. Якщо факти містять зміну (TO-BE) — чи не побудував я кейси зі старого ліміту / вигаданого проду?
7. Якщо факти містять точний текст, строк або відправку — чи не вигадав я timezone, шаблон листа чи інший канал?
8. Якщо факти містять список, фільтр, пошук або empty — чи не вигадав я пагінацію, debounce чи нечіткий пошук?

Якщо сумніваєшся — познач пункт як «потребує уточнення» замість того, щоб вигадувати деталь.

---

## Межі skill'а

Skill не знає:

- внутрішніх домовленостей команди щодо процесу;
- історії продукту та попередніх релізів;
- неописаних бізнес-правил;
- реального стану Figma-дизайну, якщо MCP не підключено.

Фінальне рішення про повноту тестового покриття залишається за QA-командою.

Детальні шаблони — у `references/`.
