# QA Test Planner

Комплексний Claude Skill для QA-інженерів: генерація тест-планів, ручних тест-кейсів, регресійних наборів, валідації дизайну проти Figma та структурованих баг-репортів.

Перед генерацією тестової документації проженіть вимогу через `requirements-review-skill`. Якщо вердикт не `Готова до тест-аналізу` — спочатку уточніть формулювання з BA.

---

## Навіщо цей skill

Прибирає рутину форматування тестової документації та тримає якісні стандарти покриття тестами, звітування про баги й валідації дизайну — без ручного дотримання шаблонів щоразу.

---

## Коли використовувати

- при створенні тест-плану для нової фічі або релізу;
- при генерації ручних тест-кейсів з чіткими кроками;
- при побудові регресійного набору (smoke, targeted, full, sanity);
- при валідації реалізації UI проти Figma-дизайну;
- при документуванні бага з чіткими кроками відтворення;
- при впровадженні стандартів тестування для команди;
- при навчанні нових QA правильному оформленню документації.

---

## Активація

Skill активується явно, за назвою:

```
/qa-test-planner
qa-test-planner
використай скіл qa-test-planner
```

---

## Як це працює

### 1. Аналіз
Розбирає опис фічі/вимоги, визначає тип потрібного тестування, обсяг, пріоритети та edge cases, які прямо випливають з тексту.

### 2. Генерація
Створює документ за перевіреним шаблоном із застосуванням QA-практик за замовчуванням.

### 3. Валідація
Перевіряє повноту документа: трасування вимога → тест-кейс, наявність очікуваних результатів на кожному кроці, логічну завершеність.

---

## Приклади використання

### Приклад 1: Тест-план

**Ввід:**
```
/qa-test-planner
Створи тест-план для фічі автентифікації користувача
```
**Вивід:** повний тест-план із метою тестування логіну/реєстрації/скидання пароля, обсягом (web + mobile), стратегією (ручне, exploratory, security), критеріями входу/виходу, оцінкою ризиків (вразливості, сторонні auth-провайдери), таймлайном.

### Приклад 2: Тест-кейси

**Ввід:**
```
/qa-test-planner
Згенеруй 5 ручних тест-кейсів для флоу оформлення замовлення
```
**Вивід:** 5 пронумерованих тест-кейсів — успішна оплата карткою, обробка невалідної картки, спроба оформлення з порожнім кошиком, застосування промокоду, оформлення як гість / як залогінений користувач. Кожен із передумовами, кроками, очікуваними результатами, тестовими даними та edge cases.

### Приклад 3: Регресійний набір

**Ввід:**
```
/qa-test-planner
Побудуй smoke-набір для модуля оплати
```
**Вивід:** пріоритезований smoke-набір (15–30 хв) із критичними шляхами (обробка платежу, повернення коштів), порядком виконання, критеріями pass/fail.

### Приклад 4: Валідація проти Figma

**Ввід:**
```
/qa-test-planner
Порівняй сторінку логіну з Figma-дизайном за посиланням [URL]
```
**Вивід:** чек-лист валідації (розміри кнопок, кольори, типографіка, відступи, стани), плюс тест-кейси на перевірку кожного елемента.

### Приклад 5: Баг-репорт

**Ввід:**
```
/qa-test-planner
Створи баг-репорт: валідація форми не блокує відправку з порожнім полем email
```
**Вивід:** структурований баг-репорт із заголовком, severity, кроками відтворення, очікуваною/фактичною поведінкою, оцінкою впливу.

---

## Пріоритети та Severity

**Пріоритет тест-кейсу:** P0 (критичний шлях) → P3 (косметика).

**Severity бага:** Critical (втрата/пошкодження даних) → Low (косметика).

---

## Основні принципи

Skill генерує документацію лише на основі наданого контексту. Він не повинен:

- вигадувати бізнес-логіку, якої немає в описі;
- вигадувати тестові дані чи дизайн-специфікації;
- завищувати severity/priority без обґрунтування;
- заповнювати edge cases «про всяк випадок», які не випливають з опису;
- змінювати структуру обраного шаблону довільно.

---

## Чек-листи якості

**Тест-план:** обсяг визначений; критерії входу/виходу є; ризики з заходами пом'якшення; реалістичний таймлайн.

**Тест-кейс:** кожен крок має результат; передумови задокументовані; тестові дані є або позначені «уточнити»; пріоритет призначений; edge cases включені обґрунтовано.

**Баг-репорт:** кроки відтворювані; середовище описане повністю; є місце для доказів; severity/priority обґрунтовані.

---

## Чого уникати

| Уникай | Чому це погано | Що робити натомість |
|---|---|---|
| Розмиті кроки | Неможливо відтворити стабільно | Конкретні дії з конкретним результатом |
| Відсутні передумови | Тести падають неочікувано | Документувати всі умови |
| Немає тестових даних | Тестувальник блокується | Приклад даних або «уточнити» |
| Загальні заголовки багів | Складно відстежувати | «[Модуль] проблема при [дії]» |
| Пропущені edge cases з опису | Пропущені реальні баги | Включати межові значення, null, порожні стани |
| Вигадані edge cases поза описом | Роздуває документ | Виносити окремим питанням, не в тест-кейс |

## Інтеграція з Figma MCP

Якщо Figma MCP підключено, skill може:

- діставати специфікації дизайну з Figma-посилання;
- генерувати пиксель-точні тест-кейси валідації;
- порівнювати реалізацію з дизайн-токенами;
- створювати баг-репорти з посиланнями на Figma для UI-розбіжностей.

Якщо MCP не підключено — розділ пропускається без вигадування даних.

## Обмеження

Skill не знає:

- внутрішніх процесів команди;
- історії продукту та попередніх релізів;
- неописаних бізнес-правил;
- реального стану Figma-дизайну без підключеного MCP.

Фінальне рішення щодо повноти тестового покриття залишається за QA-командою.
