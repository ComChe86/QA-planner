# Оплата, списання й повернення

Читай цей файл **лише** якщо в наданому тексті вже є оплата, платіж, картка, списання, checkout pay, 3DS або заявлене повернення коштів.

Це не 8-й критерій. Ті самі 7 критеріїв і та сама заборона вигадувати поведінку.

Не відкривай цей файл «про всяк випадок». Немає оплати чи повернення — не став питань про 3DS, ідемпотентність, webhook еквайра чи PCI.

Ролі, статуси й AS-IS/TO-BE — не ця лінза, якщо статус не є результатом уже заявленої оплати. Див. [actors-states-and-delta.md](actors-states-and-delta.md).

Числа, тексти повідомлень, строки й відправки — не ця лінза, якщо вони не описують саме списання / відмову / refund. Див. [values-messages-and-effects.md](values-messages-and-effects.md).

Списки замовлень і фільтр «Оплачено» — не ця лінза. Див. [lists-search-and-empty.md](lists-search-and-empty.md).

## Коли відкривати розділ

| У тексті є | Відкрий |
|---|---|
| оплата, платіж, pay, «Оплатити», картка, списання | Оплата |
| сума списання, валюта замовлення, «списується N грн» | Сума |
| відхилено, decline, «оплату не завершено» | Відмова |
| повернення коштів, refund, «повернути оплату» | Повернення |
| 3DS, SCA, повторна спроба, webhook еквайра | Лише щоб **не** вигадати їх як дефект |

Можна відкрити кілька розділів. Одна проблема — один рядок у таблиці.

## Оплата

Застосовуй існуючі критерії, якщо текст **уже заявляє** оплату.

Для заявленої оплати як окремої поведінки має бути видно:

- що вважати успіхом (статус, екран, конкретне повідомлення) **або** інший спостережуваний слід;
- якщо текст уже обіцяє відмову / decline — що саме побачить користувач.

| Ситуація | Оцінка |
|---|---|
| «Користувач оплачує карткою, система коректно проводить платіж» без видимого успіху/відмови | Повнота. Якщо оформлення вже тестоване — Major, не Critical |
| Оплата — єдина нова обіцянка без будь-якого спостережуваного результату | Повнота, зазвичай Critical |
| Успіх: статус «Оплачено» + екран «Дякуємо за замовлення»; відмова: статус лишається «Нове» + текст «Оплату не завершено» | Не `Fail`. Не вигадуй 3DS, PSP, webhook, pending |
| Story обіцяє оплату, AC або out of scope її забороняє | Несуперечність |

Не став Critical/Major за те, що не описані:

- 3DS / SCA, збережена картка, PCI, маска номера;
- назва провайдера, webhook, таймаут еквайра, ретраї;
- ідемпотентність повторного кліку, pending, часткове списання;
- чек PDF, лист-підтвердження — якщо текст їх не обіцяє.

Зразок готової оплати: [../examples/card-payment-ready.md](../examples/card-payment-ready.md).

## Сума

Застосовуй існуючі критерії, якщо текст **уже називає** суму списання або валюту замовлення.

| Ситуація | Оцінка |
|---|---|
| Дві різні суми або валюти для того самого списання (199 грн і 249 грн) | Несуперечність, Critical |
| Єдина названа сума + видимий успіх | Не `Fail`. Не вигадуй комісію, конвертацію, округлення |
| Сума не названа, але успіх і відмова вже спостережувані | Не `Fail`. Не вимагай число, якщо текст його не обіцяє |

Не став Critical/Major за те, що не описані:

- комісія еквайра, конвертація валют, округлення копійок;
- розбиття оплати (картка + бонуси), якщо спліт не заявлений;
- окрема backend-сума vs UI, якщо в тексті немає другої цифри.

Зразок Critical: [../examples/charge-amount-contradiction.md](../examples/charge-amount-contradiction.md).

## Відмова

Застосовуй існуючі критерії, якщо текст **уже обіцяє** відхилену оплату.

| Ситуація | Оцінка |
|---|---|
| «Якщо оплату відхилено» без видимого результату, і це вже заявлений негатив | Повнота. Якщо успішний шлях уже є — Major |
| Конкретний текст + статус не змінюється на «Оплачено» | Не `Fail`. Не вимагай коди банку, 3DS fail, ретраї |
| Відмова не згадана | Не `Fail`. Не вигадуй decline |

Не став Critical/Major за те, що не описані:

- причини відмови (недостатньо коштів / банк / 3DS);
- ліміт повторних спроб;
- окремий pending між кліком і відповіддю банку.

## Повернення

Застосовуй існуючі критерії, якщо текст **уже заявляє** повернення коштів.

| Ситуація | Оцінка |
|---|---|
| «Користувач може повернути оплату» без суми/умови і без видимого результату | Повнота. Якщо успішна оплата вже тестована — Major, не Critical |
| Повернення — єдина нова обіцянка без результату | Повнота, зазвичай Critical |
| Повернення повної суми, статус «Повернено», текст «Кошти повернуто» | Не `Fail`. Не вигадуй строк банку, частковий refund, chargeback |
| AC-1 повертає 199 грн, AC-2 — 249 грн за те саме замовлення | Несуперечність |

Не став Critical/Major за те, що не описані:

- строк зарахування на картку;
- часткове повернення, якщо текст його не обіцяє;
- chargeback, скасування холду vs refund;
- лист про повернення, якщо його немає в тексті.

Явне «поза скоупом: повернення коштів» — сила, не діра.

## Як записувати

1. Звичайний критерій: найчастіше Повнота (немає видимого успіху/відмови/результату refund) або Несуперечність (різні суми того самого списання).
2. Не пиши в таблиці «домен: оплата» / «домен: 3DS».
3. Не дублюй ту саму прогалину окремим рядком «немає ідемпотентності» або «немає webhook».
4. Незаявлені 3DS, PCI, PSP, ретраї, pending, чек, повторний клік — лише необов'язкове питання, ніколи Critical/Major.
5. Коротка цитата обов'язкова.
6. У готові факти клади лише названу суму/валюту, видимий успіх і відмову, заявлене повернення. Не клади вигаданий 3DS чи ідемпотентність.

У розкладі AC:

- заявлена оплата / refund без видимого результату → `блокує`;
- дві суми того самого списання → відповідні AC `блокує`;
- другорядна копія чека / тосту → `другорядний TBD`, якщо основний шлях від цього не залежить.
