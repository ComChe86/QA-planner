# Приклад рев'ю: названий перехід статусу (готова)

Калібрувальний приклад. Текст уже називає статуси й задає один перехід: звідки, тригер, новий статус і повідомлення. Вердикт має бути **Готова до тест-аналізу**.

Не вигадуй повний граф статусів продукту, проміжні статуси, таймери чи інші ролі.

---

## Вхід

Користувач може скасувати замовлення зі статусу «Нове». Після скасування статус = «Скасовано», товар повертається на склад, показується повідомлення «Замовлення скасовано».

Поза скоупом: скасування оплачених замовлень, повернення коштів.

---

## Звіт

### 1. Вердикт

✅ **Готова до тест-аналізу**

Перехід заданий повністю: джерело «Нове», новий статус, повернення товару на склад і конкретне повідомлення. Оплачені замовлення й refund явно поза скоупом — це межа обсягу, не діра.

Наступний крок після цього вердикту — skill `qa-test-planner`. Цей звіт тест-кейси не генерує.

### 2. Статус за 7 критеріями

| Критерій | Статус | Коментар |
|---|---|---|
| Атомарність | Pass | Одна поведінка: скасування нового замовлення |
| Однозначність | Pass | «Зі статусу Нове → Скасовано» має одне операційне значення |
| Повнота | Pass | Є актор, умова, новий статус і повідомлення |
| Несуперечність | Pass | Out of scope не конфліктує з описаним переходом |
| Неповторюваність | Pass | Правило сформульоване один раз |
| Тестованість | Pass | Статус, склад і повідомлення спостережувані |
| Реалізовність | Pass | Описаний перехід реалізовний без додаткових статусів |

### 4. Питання до BA

Обов'язкових питань немає.

Необов'язкові уточнення (не впливають на вердикт):

**Питання:** Чи показувати скасоване замовлення в історії користувача з тим самим статусом «Скасовано»?

**Чому це важливо:** Це місце відображення, не правило самого переходу.

Не пропоную окремий статус історії: у тексті його немає.

### 5. Що добре

- Джерело й ціль переходу названі явно.
- Є конкретне повідомлення.
- Є видима побічна дія: товар повертається на склад.
- Явне «поза скоупом» відсікає оплачені замовлення й refund.

### Готові факти

- Користувач скасовує замовлення зі статусу «Нове».
- Після цього статус = «Скасовано», товар на складі, повідомлення «Замовлення скасовано».
- Поза скоупом: скасування оплачених замовлень, повернення коштів.

## Чого цей приклад навмисно не вважає дефектом

Не став `Fail` і не піднімай вердикт через відсутність:

- повного графа статусів (В обробці, Доставлено, …);
- проміжного технічного статусу;
- таймера автоскасування;
- правила для адміністратора чи підтримки;
- сторінки 403;
- міграції вже оплачених замовлень.

Цього немає в тексті. Оплачене скасування винесене в out of scope — не питай «а що все-таки з ним?».

Якщо шлях іншої **заявленої** ролі не має результату — це вже [role-split-needs-clarification.md](role-split-needs-clarification.md), не цей приклад.

Якщо статусів узагалі немає («користувач може скасувати замовлення») — теж не вигадуй state machine і не став `Fail` лише через це.
