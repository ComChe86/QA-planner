# Приклад рев'ю: дві ролі заявлені, у однієї немає результату

Калібрувальний приклад для вердикту **Потребує уточнень**. Текст уже називає адміністратора і покупця та обіцяє обом скасування. Шлях адміністратора тестований; шлях покупця — ні.

Не вигадуй інші ролі, сторінку 403 чи повну матрицю RBAC.

---

## Вхід

Як адміністратор і як покупець я хочу скасовувати замовлення.

Acceptance criteria:

1. Адміністратор може скасувати замовлення зі статусу «Нове» або «Оплачено». Після скасування статус = «Скасовано», у стрічці подій з'являється запис «Скасовано адміністратором».
2. Покупець також може скасовувати свої замовлення.

---

## Звіт

### 1. Вердикт

⚠️ **Потребує уточнень**

Шлях адміністратора вже можна аналізувати: звідки, новий статус і видимий запис задані. Блокує те, що story й AC-2 обіцяють скасування покупцем, але не кажуть ні з яких статусів, ні що саме побачить покупець.

AC: AC-1 готовий · AC-2 блокує (немає «звідки» і видимого результату для покупця)

### 2. Статус за 7 критеріями

| Критерій | Статус | Коментар |
|---|---|---|
| Атомарність | Pass | Одна зміна: скасування замовлення двома заявленими ролями |
| Однозначність | Pass | Правило для адміністратора читається одним способом |
| Повнота | Fail | Заявлений шлях покупця не має expected result |
| Несуперечність | Pass | AC не суперечать одне одному |
| Неповторюваність | Pass | Правила не повторені з іншим змістом |
| Тестованість | Pass | Результат адміністратора спостережуваний |
| Реалізовність | Pass | Текст не вимагає неможливого |

### 3. Таблиця знахідок

| ID | Критерій | Проблема | Severity | Вплив на тест-аналіз |
|---|---|---|---|---|
| F-01 | Повнота | AC-2: «Покупець також може скасовувати свої замовлення» не задає статуси й видимий результат | Major | Не можна надійно покрити вже заявлений шлях покупця |

Не додавай другий рядок на «немає 403 для гостя» або «немає ролі підтримки»: цих ролей у тексті немає.

### 4. Питання до BA

**Питання:** З яких статусів покупець може скасувати замовлення і що саме він бачить після цього?

**Чому це важливо:** Story вже обіцяє цю роль. Без «звідки» і видимого результату неможливо задати expected result для AC-2.

**Пропонований варіант:** Покупець скасовує лише зі статусу «Нове»; статус = «Скасовано», повідомлення «Замовлення скасовано».

---

Необов'язкові уточнення (не піднімають вердикт до `Не готова`):

**Питання:** Чи однаковий запис у стрічці подій для покупця («Скасовано покупцем»)?

**Чому це важливо:** AC-1 уже задає запис для адміністратора; для покупця це копія, не ядро флоу.

### 5. Що добре

- Адміністратор має конкретні статуси-джерела і видимий результат.
- Новий статус після скасування названий.
- Дві ролі обслуговують одну дію, а не дві незалежні фічі.
- Немає прямої суперечності між AC.

### Готові факти

- Адміністратор скасовує замовлення зі статусу «Нове» або «Оплачено».
- Після цього статус = «Скасовано», у стрічці подій — «Скасовано адміністратором».
- Не готово: правило скасування для покупця (звідки + видимий результат).

---

## Чого цей приклад навмисно не вважає Critical

Не піднімай вердикт до `Не готова`: основний уже описаний шлях адміністратора тестований. Бракує результату для **вже заявленої** другої ролі.

Не став `Fail` лише тому, що не описані гість, підтримка, 403 або повна матриця прав.

Не плутай із атомарністю: каталог + фінансовий звіт — це різні інкременти, див. [mixed-features-atomicity.md](mixed-features-atomicity.md). Тут обидві ролі скасовують замовлення.

Протиставлення «статуси названі й повні»: [status-transition-ready.md](status-transition-ready.md).
